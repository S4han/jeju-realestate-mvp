# API 검증 계획 및 결과 (R-001·R-002 1차 검증 완료, 나머지 미수행)

1. Secret 존재 여부 확인(값 출력 금지).
2. 제주시/서귀포시의 매매·전월세 각각 최소 1개 월에 대해 요청 및 HTTP 상태/스키마 확인.
3. XML 구조·필드·단위·취소/정정·페이지네이션·호출 제한 확인.
4. 한국부동산원과 K-APT 주소/단지명/식별자 및 누락 범위 확인.
5. 좌표 데이터와 단지 매칭 정확도 샘플 검증.
6. 카카오맵 앱 키·도메인·무료 제공량·과금 차단 가능 여부 공식 문서/계정에서 확인.
7. PostgreSQL/호스팅 무료 이용조건·용량·상업적 이용·자동 과금 위험 검증.
8. 검증 결과를 날짜, 샘플 수, 성공/실패, 미해결 위험과 함께 기록. 실제 호출 전 사용자 승인.

실제 키·원본 응답의 민감정보는 커밋하지 않는다.

## 검증 결과 1차: R-001 매매 · R-002 전월세 (2026-10-24)

- 승인: 사용자 승인 "실거래 API 검증 호출 14건 이내" → **12건 사용**(성공 9 / 연결 끊김 3), 2건 미사용
- 환경: Claude Code 클라우드 세션, 에이전트 프록시 경유, 키는 환경변수 `DATA_GO_KR_SERVICE_KEY`(Decoding 키, 값 미출력), 요청 로그에서 키 마스킹
- 원본 응답은 저장소에 커밋하지 않음(세션 임시 디렉터리에만 보관)
- 일일 트래픽 한도: 마이페이지 값 미확인(사용자 확인 필요)

### 매매 응답 필드 (✅ 실측, 281행)
`aptNm, aptDong, buildYear, buyerGbn, slerGbn, cdealDay, cdealType, dealAmount, dealYear, dealMonth, dealDay, dealingGbn, estateAgentSggNm, excluUseAr, floor, jibun, landLeaseholdGbn, rgstDate, sggCd, umdNm`

- ❗ **단지 일련번호(`aptSeq`), 법정동코드, 도로명, 본번/부번 필드가 없습니다.** 매매에서 위치를 알려주는 값은 `sggCd + umdNm(법정동명) + jibun(지번 문자열) + aptNm`뿐입니다.
- `dealAmount`: 만원 단위, 콤마가 들어간 문자열입니다(예 `40,300`). 원 단위로 바꾸려면 ×10,000을 합니다.
- `excluUseAr`: 전용면적(㎡) 소수 문자열, `floor`: 정수 문자열입니다(표본 최소값 1, 지하층 표기는 미확인).
- 계약일은 `dealYear`/`dealMonth`/`dealDay`로 나뉘어 있습니다.
- `aptDong`은 비어 있는 경우가 많고(32/104), 표기도 `102동`, `105`, `도남1차e-편한세상 101`처럼 제각각입니다.
- `rgstDate`(등기일, `YY.MM.DD`)는 시간이 지나면서 채워집니다(2026-04 계약 131/148, 2026-08 계약 82/133).

### 전월세 응답 필드 (✅ 실측, 421행)
`aptNm, aptSeq, buildYear, contractTerm, contractType, dealYear, dealMonth, dealDay, deposit, monthlyRent, preDeposit, preMonthlyRent, excluUseAr, floor, jibun, sggCd, umdNm, useRRRight, roadnm, roadnmbcd, roadnmbonbun, roadnmbubun, roadnmcd, roadnmseq, roadnmsggcd`

- ✅ **전월세에는 `aptSeq`(형식 `50110-4712`)와 도로명 주소 코드가 있습니다.**
- `deposit`/`monthlyRent`: 만원 단위 문자열이고, 월세 0이면 전세입니다. 보증금과 월세는 별도 필드로 옵니다(AT-010 충족 가능).
- `contractType`(신규/갱신), `contractTerm`(`26.09~28.09`), `preDeposit`/`preMonthlyRent`(갱신 시 종전 조건)가 있습니다.
- 표본에서 `aptSeq` ↔ (`sggCd`, `umdNm`, `jibun`)은 1:1이었습니다(175개 단지, 충돌 0건).

### 해제(취소) 처리 (✅ 실측)
- 해제된 거래는 응답에서 **빠지지 않고**, `cdealType=O`와 `cdealDay`(해제일 `YY.MM.DD`)가 채워진 채로 남아 있습니다.
- 해제는 몇 달 뒤에도 생깁니다. 2026-04 계약 148건 중 13건이 해제되었고, 그중 해제일이 2026-09-22인 건도 있습니다. 2026-08 계약은 104건 중 4건이 해제되었습니다.
- 같은 조건의 거래가 **"해제된 원거래 + 재신고된 정상 거래"** 2행으로 나오는 사례가 있었습니다(중복 키 11그룹 중 10그룹). 따라서 해제 행을 덮어쓰지 말고 별도 행으로 보관해야 합니다. 화면에는 해제 행을 표시하지 않거나 "해제" 표기를 붙입니다.

### 원천 고유키 (✅ 실측: 없음)
- 매매와 전월세 모두 거래 고유 ID가 없습니다.
- 매매의 복합키(sgg+법정동+지번+단지명+면적+층+계약일+금액)는 해제/재신고 쌍에서만 충돌했습니다.
- 전월세는 aptSeq+면적+층+계약일+보증금+월세+계약기간+구분까지 **모든 필드가 같은 행이 12그룹** 있었습니다(421행 중). 중복 신고인지, 같은 날 같은 층에서 맺은 서로 다른 계약인지 구분할 수 없습니다.
  → 설계 제안: 자연키 + **같은 키 안에서의 순번(occurrence)** 으로 저장하고, 재수집 시 키별 건수로 비교합니다. 임의로 중복을 제거하지 않습니다.

### 페이지네이션·오류 동작 (✅ 실측)
- 매매는 `numOfRows=1000`이 정상입니다. **전월세는 1000에서 매번 연결이 끊기고(3/3), 400은 정상입니다.** 운영 페이지 크기는 **400 이하**로 하고 `totalCount` 기준으로 페이지를 반복합니다.
- **잘못된 파라미터를 보내면 오류 XML 대신 연결이 끊깁니다**(약 7~12초 후). 원천 서버 문제와 네트워크 문제를 응답만으로 구분할 수 없으므로, 둘 다 "수집 실패"로 기록하고 백오프 재시도 → 실패 시 마지막 정상 데이터를 유지합니다.
- 데이터가 없는 달은 `200/000 + totalCount=0`으로 옵니다. 이것을 "거래 없음"으로 처리하고, 연결 실패와 구분합니다.
- 연결이 끊긴 호출이 일일 트래픽에 집계되는지는 미확인입니다.

### 동명 단지 (✅ 실측)
- 매매 표본에서 같은 단지명인데 위치가 다른 경우가 2건 있었습니다. 예) `송우수자인`은 노형동 905-10과 940-7, `미듬아뜨리에`는 삼도이동과 오라이동. 단지명만으로 연결하지 않는다는 원칙이 필요함을 실데이터로 확인했습니다.

### 규모·호출 예산 (실측 기반 추정)
- 2026-08 기준 월 건수: 제주시 매매 104·전월세 315, 서귀포시 매매 29·전월세 106 → 월 약 550건, **12개월 약 7천 행**입니다. DB 용량은 수 MB 수준으로 무료 한도(500MB) 대비 여유가 큽니다.
- 호출량 추정: 초기 전체 수집은 (2시 × 2유형 × 12개월) 약 48~60호출, 일일 증분(최근 4개월)은 약 16~20호출입니다. 개발계정 한도 대비 매우 작습니다.

### 미해결·후속
1. **매매 매칭 키 부족**: 매매 응답에 `aptSeq`·도로명이 없습니다. "아파트 매매 실거래가 **상세** 자료" API를 활용신청하면 aptSeq·도로명이 포함되는지 확인이 필요합니다(❓, 추가 승인 필요). 받지 못하면 매매 매칭은 법정동명+지번+단지명 3중 일치와 단지 기준정보 대조로만 확정합니다.
2. 전월세 `numOfRows` 정확한 상한(400~999 사이)은 미확인입니다. 운영은 400으로 고정합니다.
3. 일일 트래픽 한도는 사용자가 마이페이지에서 확인해야 합니다.
4. 지하층(음수 floor), 해제 사유 필드 유무는 표본에 없었습니다.
5. EXT-003~006(단지정보·카카오·좌표), DB·호스팅 무료 조건은 아직 검증하지 않았습니다.

  3. 매매 `aptSeq`와 전월세 `aptSeq`가 같은 단지에 같은 값을 쓰는지

## 검증 결과 2차: 매매 상세 API (2026-10-24)

- 승인: 사용자 승인 "매매 상세 API 검증 호출 2건" → **2건 사용, 2건 모두 성공**
- 호출 기록

| # | 대상 | numOfRows | 결과 | totalCount | 응답시간 |
|---|---|---|---|---|---|
| D1 | 제주시 매매 상세 2026-08 | 1000 | 200/000 | 104 | 1.42s |
| D2 | 서귀포시 매매 상세 2026-08 | 1000 | 200/000 | 29 | 0.85s |

### 확인 결과 (✅ 실측)
- **`aptSeq`가 133행 전부 채워져 있다**(제주시 `50110-366`, 서귀포시 `50130-870` 형식). `umdCd`, `landCd`, `bonbun`/`bubun`, `roadNm`, `roadNmCd`, `roadNmBonbun`/`roadNmBubun`도 전부 채워져 있다. 단 `roadNmbCd`(지상/지하 구분)는 일부 비어 있다(99/104, 23/29).
- **기본 매매 API와 같은 거래 집합이다**: 공통 필드 12개(시군구·법정동·지번·단지명·면적·층·일·금액·해제여부·해제일·등기일·동)를 기준으로 비교하면 두 API의 행 집합이 완전히 같다(133행). 따라서 **매매는 상세 API 하나로 수집하고, 기본 API는 쓰지 않는다**(호출량도 절반).
- `jibun`은 `bonbun`/`bubun`에서 앞의 0을 뺀 값과 133행 모두 일치한다.
- 표본 안에서 `aptSeq` ↔ (`umdCd`, `bonbun`, `bubun`)은 1:1이다(99개 단지, 충돌 0건). 같은 단지명이 여러 `aptSeq`에 쓰인 사례는 이번 표본(1개월)에는 없었다.
- **매매와 전월세의 `aptSeq`가 같은 체계다**: 매매 단지 99개 중 37개가 같은 달 전월세에도 등장했다. 37개 모두 법정동·지번이 같았고 단지명도 같았다(불일치 0건). → 매매와 전월세를 `aptSeq`로 묶을 수 있다.
- `umdNm`이 읍면 지역에서는 `구좌읍 세화리`, `남원읍 위미리`처럼 **읍면+리** 형태로 온다. 주소를 정규화할 때 반영해야 한다.

### 매칭 설계에 주는 영향
- 실거래끼리 같은 단지인지는 원천이 준 `aptSeq`로 판정하면 된다(1단계, 확정).
- `aptSeq`와 단지 기준정보(한국부동산원 단지 식별정보·K-APT)를 연결하는 일이 TASK-003·005의 핵심 과제가 된다. 연결 키 후보는 `sggCd+umdCd+bonbun+bubun`(지번 PNU 구성요소)과 도로명 코드다. 이것이 맞는지는 단지정보 API를 실제로 호출해 확인해야 한다.
- `aptSeq`가 무엇을 가리키는 식별자인지(단지 단위인지, 동일 지번 내 여러 단지는 어떻게 되는지)는 공식 정의를 확인하지 못했다. 12개월 데이터로 1:1 관계를 다시 검증한다.

### 자동 플래그(마커 보류 후보, 약 5%)
- 지목이 `대`(대지)가 아닌 필지 7건(`전` 5, `과` 1, `잡` 1). 예) 그린트리(애월리, 전), 동명(고성리, 잡). 지적도 지목 갱신 지연 또는 PNU 오류 가능성이 있다.
- 면적 300㎡ 미만 49건. 예) 세기에코빌 99세대가 200㎡. 여러 필지로 된 단지에서 작은 필지가 대표 PNU로 잡힌 것으로 보인다.
- 100세대 이상인데 면적 1,000㎡ 미만 5건. 예) 제주연동리슈빌디에스 158세대가 345㎡.
→ 이 경우는 `location_status=REVIEW`로 두고, 확인 전에는 마커를 만들지 않는 것을 제안한다. 필지 안의 점이라 단지 부지 근처일 가능성은 높지만 검증되지 않았다.
